# 設計メモ（講師向け）

ハンズオンの構成で、あえて選んでいることと、その理由を残しておく。

## デプロイ先は Model Serving（Databricks Apps ではない）

- 現在の Databricks の推奨は、新しく作るエージェントを **Databricks Apps** にデプロイする方式（Agent Bricks CLI）。
  Model Serving へのデプロイ（`databricks.agents.deploy`）は、それより前からある方式。
- このハンズオンでは次の理由で Model Serving を使う。
  - デプロイすると **Review App**（人のフィードバックを集める画面）がすぐ使え、評価の流れ（オフライン評価 → 人のフィードバック）を一続きで体験できる。
  - 見極めジョブ（バッチ）からエンドポイントを呼ぶ、既存の仕組みと同じ形にしている。
- 実際の開発で新しくエージェントを作る場合は、Databricks Apps へのデプロイも検討する。

## Managed Agent Memory は旧方式（Unity Catalog の MEMORY_STORE）を使う

- Memory には 2 つの方式がある。
  | | 旧方式 | 新方式（Beta） |
  |---|---|---|
  | 実体 | Unity Catalog のオブジェクト（`MEMORY_STORE`） | Lakebase 上のストア（ワークスペース単位） |
  | API | `/api/2.1/unity-catalog/memory-stores/...` | `/api/2.0/agents/memory-stores/...` |
  | 記憶の単位 | `scope` + `path` | `actor_id` + `path` |
  | 公式ドキュメントの扱い | legacy（提供終了の予定あり） | 後継 |
- **このハンズオンは旧方式を使う。** Model Serving にデプロイしたエージェントから、呼び出したユーザーの代理（OBO）で
  読み書きできるのが旧方式だけのため。
  - 旧方式: OBO のスコープ `unity-catalog` で読み書きできる（エンドポイントは `UserAuthPolicy(api_scopes=["unity-catalog"])` でデプロイ）。
  - 新方式: OBO のトークンでは `required scopes: mason` で拒否される。`mason` は Model Serving の OBO で指定できるスコープに
    含まれていない（指定するとモデルの登録時にエラー）。エンドポイント自身の ID に権限を付ければ使えるが、
    その ID はデプロイのたびに変わるため、ハンズオンでは扱いにくい。
  - 新方式とそのライブラリ（`databricks-agentbricks`）は Databricks Apps へのデプロイを前提に作られているとみられ、
    Model Serving からは認証がうまくつながらない。
- 旧方式が提供終了になる前に、デプロイ先を Databricks Apps に、Memory を新方式に移す必要がある。

## Memory は検索ではなく一覧で読む

- 1 つの scope（会社・ルール）の記憶は数件なので、エージェントは scope の記憶を一覧で全部読む。
- 検索（`entries:search`）は、日本語の短い語で見つからないことがあった（新方式で確認）。採点の前提になる記憶を取りこぼさないため、一覧にした。

## 評価データ（3 件）はわざと NG が出るようにしている

| 評価データ | NG の内容 | 直し方 | 学ぶこと |
|---|---|---|---|
| E001 | CRM では競合が導入済みのため、関係性の補正が −6〜−10 になる。期待は −5〜0 | Memory（scope=E001）に営業の申し送り「競合の契約は 2026 年 12 月末で満了・更新しない方針」を足す | 長期記憶で、CRM にない事情を採点に反映する |
| E002 | ④企業規模で従業員 4,000 人が段階 3 になる。期待は段階 4 | 採点基準（`rubric.py`）の段階 4 の境界を 3,000 人以上に下げる | 評価データは業務部門の判断を表す。判断が決まったら採点基準を直す |
| E003 | 情報が足りない観点があるのに、次のアクションに確認事項がない | まとめのプロンプト（`rubric.py` の `SUMMARY_PROMPT`）に、情報不足の観点の確認事項を書く指示を足す | 文章の品質は LLM ジャッジで測り、プロンプトで直す |

- 期待値は、どの評価データでも同じ 2 項目（`expected_tier` と `expected_points`）にしている。お客様が評価データを作るときに、
  「この件はこの項目を埋める、この件は埋めない」を判断しなくて済むようにするため（あるべき Tier と、あるべき答えのポイントを書くだけ）。
  細かい期待（補正の範囲、観点の段階、次のアクションの書き方）は、`expected_points` の文章で書き、LLM ジャッジで判定する。
- どれも、直す前は確実に NG（ポイントだけが NG で、Tier は合う）になり、直した後は確実に OK になることを確かめてある
  （LLM の気まぐれで合否が変わらないよう、点数が Tier の境目から離れるように企業特性を作っている）。
- 当初は「時期の書かれていない当局の指摘を⑤の段階 4 にする」案だったが、直す前から段階 4 になることがあり、採用しなかった。

## 評価では Memory に書き込まない

- エージェントは `custom_inputs.save_history` が true のときだけ、採点の結果を会社別の Memory に書き込む。
- ジョブ（Step 5）だけが true で呼ぶ。評価で書き込むと、次の評価で前回の採点結果を参照してしまい、評価の結果が変わるため。
